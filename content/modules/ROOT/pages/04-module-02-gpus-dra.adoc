= 模块 2：DRA 方式使用 GPU
:navtitle: 模块 2：DRA 方式使用 GPU

GPU 是 AI 集群上最昂贵的资源，客户通常会首先提出两个问题：_工作负载如何获取 GPU？多个工作负载能否共享同一块 GPU？_ 多年来，答案是设备插件（device plugin）：节点声明 `nvidia.com/gpu: 1`，Pod 请求一个，这就是调度器所知道的全部。Kubernetes Dynamic Resource Allocation（DRA）用每个设备的完整描述取代了这个计数器，包括型号、显存、架构和驱动信息，并允许工作负载按属性请求设备，以及显式地共享设备。

在本模块中，您将让集群识别 GPU，加载 NVIDIA 驱动程序，启用 NVIDIA DRA 驱动，读取 L4 GPU 的发布信息，并以三种方式申请该 GPU：独占使用、使用无法匹配的属性选择器，以及两个 Pod 共享同一块 GPU。

.初次接触 DRA？
[%collapsible]
====
* *DeviceClass* — 由选择器定义的集群级设备类别（例如"NVIDIA GPU"）；工作负载按类别申请设备。
* *ResourceSlice* — DRA 驱动为每个节点发布的资源切片：列出该节点上的所有设备及其属性和容量。
* *ResourceClaim* — 对设备的申请，由调度器分配到具体设备；引用同一申请的 Pod 共享其设备。
* *ResourceClaimTemplate* — 模板，Kubernetes 为每个 Pod 创建一个新申请，使每个 Pod 获得独立的设备。
* *CEL（Common Expression Language）* — 申请用来按属性选择设备的表达式语言，例如 `device.attributes['gpu.nvidia.com'].productName == 'NVIDIA L4'`。
====

== 技术背景

NVIDIA GPU Operator（本例为 {gpu_operator_version}）可在 GPU 节点上构建两种不同的栈：

[cols="1,2,2",options="header"]
|===
| | 设备插件栈（`ClusterPolicy`） | DRA 栈（`GPUCluster`）

| 调度器所见
| 节点上的整数 `nvidia.com/gpu: 1`
| 列出每块 GPU 及其属性的 `ResourceSlice`（产品名、显存、架构、驱动和 CUDA 版本、PCI 地址）

| Pod 申请方式
| `resources.limits: nvidia.com/gpu: 1`
| `resourceClaims` 指向一个 `ResourceClaim` 或 `ResourceClaimTemplate`，可按属性选择

| 共享方式
| 在 Pod 规格之外按节点配置（time-slicing、MPS）
| 在 API 中显式指定：引用同一申请的 Pod 共享其设备

| 分配者
| kubelet 的设备管理器选择设备
| 调度器在放置 Pod 之前分配申请，并记录所选设备
|===

驱动程序与两种栈分开安装：`NVIDIADriver` CR 在其选中的每个节点上运行一个驱动容器，加载 NVIDIA 内核模块。`GPUCluster` CR 随后运行 NVIDIA DRA 驱动（每个 GPU 节点上的 kubelet 插件），通过已加载的驱动发现 GPU 并以 ResourceSlice 形式发布，同时运行 DCGM exporter 采集 GPU 指标。Kubernetes {ocp_version} 的调度器完成其余工作：DRA（`resource.k8s.io/v1`）是稳定的 Kubernetes API。

本工作坊其余部分使用 DRA 栈，因此第 1 天和第 2 天的所有 GPU 工作负载，包括模型服务器，都通过申请（Claim）获取 GPU。

IMPORTANT: 请勿在此集群上创建 `ClusterPolicy`。两种栈不能同时管理同一个 GPU 节点。

// NOT-IN-DOCS: OpenShift AI 3.5 通过设备插件和硬件配置文件记录 GPU；GPUCluster DRA 栈来自 NVIDIA（GPU Operator 26.7 中的 v1alpha1 API）。详见参考页面。
NOTE: `GPUCluster` API 在 GPU Operator {gpu_operator_version} 中为 `v1alpha1`，OpenShift AI {rhoai_version} 通过设备插件和硬件配置文件记录 GPU 访问。本模块直接讲授 DRA 机制；关于其支持含义，请参阅 xref:91-reference.adoc[技术参考]。

== 学习目标

* 启用硬件发现，通过 NFD 标签找到 GPU 节点。
* 使用 `NVIDIADriver` CR 加载 NVIDIA 驱动，并用 `nvidia-smi` 验证。
* 使用 `GPUCluster` CR 启用 NVIDIA DRA 驱动。
* 从 `ResourceSlice` 中读取 GPU 属性，并解释 `DeviceClass` 的选择方式。
* 使用 `ResourceClaimTemplate` 和 CEL 选择器申请 GPU，并读取分配结果。
* 展示独占申请会阻止第二个 Pod，不满足的选择器会阻止 Pod，以及共享 `ResourceClaim` 允许两个 Pod 使用同一块 GPU。

== 练习 1：让集群识别 GPU

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m2-ex1.mp4[width=100%]

Node Feature Discovery 已安装，但只有在创建实例后才开始扫描节点。`NodeFeatureDiscovery` CR 在每个节点上启动一个 worker，读取 PCI 总线并为节点打上设备类别和厂商标签。NVIDIA 的 PCI 厂商 ID 是 `10de`。

[source,yaml]
----
kind: NodeFeatureDiscovery
spec:
  workerConfig:
    configData: |
      sources:
        pci:
          deviceClassWhitelist: ["0200", "03", "12"]   # <1>
          deviceLabelFields: ["vendor"]                 # <2>
----
<1> *deviceClassWhitelist* — 要上报的 PCI 类别：网络控制器（`0200`）、显示控制器（`03`，包含 GPU）和处理加速器（`12`）。
<2> *deviceLabelFields* — 按厂商 ID 打标签，生成 `feature.node.kubernetes.io/pci-<vendor>.present=true`。

[source,bash,role="execute"]
----
oc apply -f - <<'EOF'
apiVersion: nfd.openshift.io/v1
kind: NodeFeatureDiscovery
metadata:
  name: nfd-instance
  namespace: openshift-nfd
spec:
  operand:
    imagePullPolicy: IfNotPresent
    servicePort: 12000
  workerConfig:
    configData: |
      core:
        sleepInterval: 60s
      sources:
        pci:
          deviceClassWhitelist: ["0200", "03", "12"]
          deviceLabelFields: ["vendor"]
EOF
for i in $(seq 1 30); do
  n=$(oc get nodes -l feature.node.kubernetes.io/pci-10de.present=true -o name)
  [ -n "$n" ] && break; echo "waiting for NFD labels..."; sleep 10
done
oc get nodes -l feature.node.kubernetes.io/pci-10de.present=true \
  -o custom-columns=NODE:.metadata.name,INSTANCE:.metadata.labels.node\\.kubernetes\\.io/instance-type
----

预期结果：经过几行 `waiting for NFD labels...` 后，列出一个节点，即模块 1 中找到的 `g6.2xlarge` GPU 节点。集群现在知道哪个节点有 NVIDIA 设备；后续所有 NVIDIA 组件都通过此标签选择节点。

== 练习 2：加载 NVIDIA 驱动

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m2-ex2.mp4[width=100%]

`NVIDIADriver` CR 告诉 GPU Operator 在哪些节点上运行哪个驱动镜像。Operator 附带一个固定版本的驱动镜像；以下 CR 使用其摘要并通过练习 1 的 NFD 标签选择节点。

IMPORTANT: 只有在 `GPUCluster` 或 `ClusterPolicy` 存在后，GPU Operator 才会为 GPU 节点打标签（`nvidia.com/gpu.present`），驱动也只在已打标签的节点上运行。因此下面的代码块同时创建练习 3 中解释的 `GPUCluster`；没有它，`NVIDIADriver` 会报告 `ready`，但实际上没有运行任何驱动。

[source,yaml,subs="attributes+"]
----
apiVersion: nvidia.com/v1alpha1
kind: NVIDIADriver
spec:
  driverType: gpu                                   # <1>
  repository: nvcr.io/nvidia
  image: driver
  version: "{gpu_driver_digest}"                   # <2>
  nodeSelector:
    feature.node.kubernetes.io/pci-10de.present: "true"   # <3>
  tolerations:
  - {key: nvidia.com/gpu, operator: Exists, effect: NoSchedule}   # <4>
----
<1> *driverType* — `gpu` 适用于裸金属或直通 GPU（其他选项为 vGPU 模式）。
<2> *version* — Operator 发布时附带的驱动镜像摘要（其 `driver-image` 相关镜像）。
<3> *nodeSelector* — 仅在 NFD 发现 NVIDIA PCI 设备的节点上运行驱动。
<4> *tolerations* — GPU 节点有污点，驱动 Pod 必须容忍该污点。

[source,bash,role="execute",subs="attributes+"]
----
oc apply -f - <<'EOF'
apiVersion: nvidia.com/v1alpha1
kind: NVIDIADriver
metadata:
  name: gpu-driver
spec:
  driverType: gpu
  repository: nvcr.io/nvidia
  image: driver
  version: "{gpu_driver_digest}"
  nodeSelector:
    feature.node.kubernetes.io/pci-10de.present: "true"
  tolerations:
  - key: nvidia.com/gpu
    operator: Exists
    effect: NoSchedule
EOF
oc apply -f - <<'EOF'
apiVersion: nvidia.com/v1alpha1
kind: GPUCluster
metadata:
  name: gpu-cluster
spec:
  draDriver:
    computeDomains:
      enabled: false
  daemonsets:
    tolerations:
    - key: nvidia.com/gpu
      operator: Exists
      effect: NoSchedule
  dcgmExporter:
    enabled: true
EOF
----

预期结果：`nvidiadriver.nvidia.com/gpu-driver created` 和 `gpucluster.nvidia.com/gpu-cluster created`。仅创建并不能说明问题；下一步等待驱动加载。

驱动容器需要几分钟来启动并加载内核模块。等待 CR 报告 `ready`：

[source,bash,role="execute"]
----
for i in $(seq 1 60); do
  s=$(oc get nvidiadriver gpu-driver -o jsonpath='{.status.state}')
  DRIVER_POD=$(oc get pods -n nvidia-gpu-operator -o name | grep nvidia-gpu-driver | head -1)
  r=$([ -n "$DRIVER_POD" ] && oc get -n nvidia-gpu-operator "$DRIVER_POD" -o jsonpath='{.status.containerStatuses[?(@.name=="nvidia-driver-ctr")].ready}')
  [ "$r" = true ] || s="${s:-pending}, waiting for the driver pod"
  echo "driver state: $s"; [ "$s" = ready ] && break; sleep 10
done
oc exec -n nvidia-gpu-operator "$DRIVER_POD" -c nvidia-driver-ctr -- \
  nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv
----

预期结果：`driver state: …, waiting for the driver pod` 重复三到五分钟，驱动容器构建并加载内核模块后，循环在 `driver state: ready`（CR 就绪，驱动 Pod 已 Ready）时结束，`nvidia-smi` 打印一行：`NVIDIA L4, 23034 MiB, 595.91.07`（或 Operator 附带的驱动版本）。内核驱动已加载并与 GPU 通信，但调度器仍无法分配它——这是下一个练习的内容。

简言之：驱动使 GPU 在节点上可用；但不使其对调度器可见。

== 练习 3：启用 DRA 驱动

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m2-ex3.mp4[width=100%]

您在练习 2 中已创建了 `GPUCluster`，以便驱动可以部署；以下是它运行的内容。重新应用不会有任何变化。

[source,yaml]
----
apiVersion: nvidia.com/v1alpha1
kind: GPUCluster
spec:
  draDriver:
    computeDomains:
      enabled: false        # <1>
  daemonsets:
    tolerations:            # <2>
    - {key: nvidia.com/gpu, operator: Exists, effect: NoSchedule}
  dcgmExporter:
    enabled: true           # <3>
----
<1> *computeDomains* — 多节点 NVLink 域（适用于 GB200 级系统）；单块 L4 不需要。
<2> *daemonsets.tolerations* — 该栈运行的每个 DaemonSet（DRA kubelet 插件、验证器、exporter）都必须容忍 GPU 污点。
<3> *dcgmExporter* — 将 GPU 利用率和显存指标发布到 Prometheus。

[source,bash,role="execute"]
----
oc apply -f - <<'EOF'
apiVersion: nvidia.com/v1alpha1
kind: GPUCluster
metadata:
  name: gpu-cluster
spec:
  draDriver:
    computeDomains:
      enabled: false
  daemonsets:
    tolerations:
    - key: nvidia.com/gpu
      operator: Exists
      effect: NoSchedule
  dcgmExporter:
    enabled: true
EOF
for i in $(seq 1 30); do
  s=$(oc get gpucluster gpu-cluster -o jsonpath='{.status.state}')
  echo "gpucluster state: ${s:-pending}"; [ "$s" = ready ] && break; sleep 10
done
oc get pods -n nvidia-gpu-operator
----

预期结果：`gpucluster.nvidia.com/gpu-cluster unchanged`，循环在 `gpucluster state: ready` 时结束，`nvidia-gpu-operator` 中运行着 `nvidia-dra-driver-kubelet-plugin-…`、`nvidia-dra-validator-…` 和 `nvidia-dcgm-exporter-dra-…`（以及驱动 Pod），全部为 `Running`。没有设备插件 Pod：此栈从不声明 `nvidia.com/gpu`。

== 练习 4：读取 DRA 发布的信息

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m2-ex4.mp4[width=100%]

[source,bash,role="execute"]
----
oc get deviceclass
oc get deviceclass gpu.nvidia.com -o jsonpath='{.spec.selectors[0].cel.expression}{"\n"}'
oc get resourceslices -o jsonpath='{range .items[*]}{.spec.nodeName}{"\n"}{range .spec.devices[*]}  {.name}: {.attributes.productName.string}, {.attributes.architecture.string}, memory {.capacity.memory.value}, driver {.attributes.driverVersion.version}, CUDA {.attributes.cudaComputeCapability.version}{"\n"}{end}{end}'
----

预期结果：三个设备类别 `gpu.nvidia.com`、`mig.nvidia.com` 和 `vfio.gpu.nvidia.com`；`gpu.nvidia.com` 的选择器为 `device.driver == 'gpu.nvidia.com' && device.attributes['gpu.nvidia.com'].type == 'gpu'`；GPU 节点的 ResourceSlice 列出一个设备：`gpu-0: NVIDIA L4, Ada Lovelace, memory 23034Mi, driver 595.91.7, CUDA 8.9.0`。调度器现在知道该设备_是什么_，而不仅仅是存在一个设备。

简言之：DeviceClass 是对驱动在 ResourceSlice 中发布的属性进行过滤的选择器。

== 练习 5：通过属性申请 GPU

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m2-ex5.mp4[width=100%]

创建一个用于 GPU 测试的 Project、一个申请 `gpu.nvidia.com` 类别中产品名为 `NVIDIA L4` 的设备的 `ResourceClaimTemplate`，以及一个使用它的 Pod。

[source,yaml,subs="attributes+"]
----
kind: ResourceClaimTemplate
spec:
  spec:
    devices:
      requests:
      - name: gpu
        exactly:
          deviceClassName: gpu.nvidia.com          # <1>
          selectors:
          - cel:
              expression: device.attributes['gpu.nvidia.com'].productName == 'NVIDIA L4'   # <2>
---
kind: Pod
spec:
  resourceClaims:
  - name: gpu
    resourceClaimTemplateName: one-l4               # <3>
  containers:
  - resources:
      claims: [{name: gpu}]                         # <4>
----
<1> *deviceClassName* — 要从中选择的类别。
<2> *selectors* — 对设备已发布属性进行 CEL 过滤；只有匹配的设备才是候选。
<3> *resourceClaimTemplateName* — Kubernetes 从模板为此 Pod 创建新申请。
<4> *resources.claims* — 哪个容器获得申请的设备。

[source,bash,role="execute",subs="attributes+"]
----
oc new-project {gpu_namespace} >/dev/null 2>&1 || oc project {gpu_namespace}
oc apply -n {gpu_namespace} -f - <<'EOF'
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: one-l4
spec:
  spec:
    devices:
      requests:
      - name: gpu
        exactly:
          deviceClassName: gpu.nvidia.com
          selectors:
          - cel:
              expression: device.attributes['gpu.nvidia.com'].productName == 'NVIDIA L4'
EOF
# 先创建 smi-a，待其持有 GPU 后再创建 smi-b：顺序决定哪个 Pod 获得设备。
for p in smi-a smi-b; do
oc apply -n {gpu_namespace} -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: $p
spec:
  restartPolicy: Never
  tolerations: [{key: nvidia.com/gpu, operator: Exists, effect: NoSchedule}]
  securityContext: {runAsNonRoot: true, seccompProfile: {type: RuntimeDefault}}
  resourceClaims:
  - name: gpu
    resourceClaimTemplateName: one-l4
  containers:
  - name: smi
    image: {cuda_image}
    command: ["bash", "-c", "nvidia-smi -L; sleep 3600"]
    securityContext: {allowPrivilegeEscalation: false, capabilities: {drop: [ALL]}}
    resources:
      claims: [{name: gpu}]
EOF
[ "$p" = smi-a ] && oc wait -n {gpu_namespace} --for=condition=Ready pod/smi-a --timeout=300s
done
oc logs -n {gpu_namespace} smi-a
oc get resourceclaims -n {gpu_namespace} \
  -o custom-columns=CLAIM:.metadata.name,STATE:.status.allocation.devices.results[0].device,RESERVED_FOR:.status.reservedFor[*].name
----

预期结果：`smi-a` 变为 Ready 并打印 `GPU 0: NVIDIA L4 (UUID: GPU-…)`。存在两个申请，每个 Pod 一个，均由模板创建：`smi-a-gpu-…` 分配到设备 `gpu-0` 并为 `smi-a` 保留；`smi-b-gpu-…` 没有设备。调度器在放置 Pod 之前完成了 GPU 分配。

== 练习 6：两个负向验证

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m2-ex6.mp4[width=100%]

第二个 Pod 申请了自己的 GPU，但集群只有一块，第一个 Pod 已持有它。

[source,bash,role="execute",subs="attributes+"]
----
oc get pod smi-b -n {gpu_namespace} -o jsonpath='{.status.phase}{"\n"}'
oc get events -n {gpu_namespace} --field-selector involvedObject.name=smi-b,reason=FailedScheduling \
  -o jsonpath='{.items[-1:].message}{"\n"}'
----

预期结果：`smi-b` 为 `Pending`，最后一条 `FailedScheduling` 事件显示 `0/8 nodes are available: 3 node(s) had untolerated taint(s), 5 cannot allocate all claims. …`（节点数取决于您的集群）：三个控制平面节点因 Pod 不容忍的污点而被排除，其余所有节点（包括 GPU 节点）都没有设备能满足该申请。独占申请确实是独占的：调度器不会将第二个 Pod 放置在已分配给其他 Pod 的 GPU 上。

现在释放 GPU，并申请此集群上不存在的设备——H100：

[source,bash,role="execute",subs="attributes+"]
----
oc delete pod smi-a smi-b -n {gpu_namespace} --wait=true
oc apply -n {gpu_namespace} -f - <<EOF
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: one-h100
spec:
  spec:
    devices:
      requests:
      - name: gpu
        exactly:
          deviceClassName: gpu.nvidia.com
          selectors:
          - cel:
              expression: device.attributes['gpu.nvidia.com'].productName.startsWith('NVIDIA H100')
---
apiVersion: v1
kind: Pod
metadata:
  name: smi-h100
spec:
  restartPolicy: Never
  tolerations: [{key: nvidia.com/gpu, operator: Exists, effect: NoSchedule}]
  securityContext: {runAsNonRoot: true, seccompProfile: {type: RuntimeDefault}}
  resourceClaims:
  - name: gpu
    resourceClaimTemplateName: one-h100
  containers:
  - name: smi
    image: {cuda_image}
    command: ["bash", "-c", "nvidia-smi -L; sleep 3600"]
    securityContext: {allowPrivilegeEscalation: false, capabilities: {drop: [ALL]}}
    resources:
      claims: [{name: gpu}]
EOF
sleep 20
oc get pod smi-h100 -n {gpu_namespace} -o jsonpath='{.status.phase}{"\n"}'
oc get events -n {gpu_namespace} --field-selector involvedObject.name=smi-h100,reason=FailedScheduling \
  -o jsonpath='{.items[-1:].message}{"\n"}'
----

预期结果：即使 GPU 已释放，`smi-h100` 仍保持 `Pending` 状态，原因同样是 `cannot allocate all claims`：唯一 GPU 的 `productName` 是 `NVIDIA L4`，选择器无法匹配任何设备。选择器由调度器强制执行，而非由工作负载决定。

.此练习的脚本化断言
[%collapsible]
====
在 `smi-h100` 仍存在时运行。只有当 Pod 因申请不满足而未被调度（且 GPU 空闲）时，断言才通过。

[source,bash,subs="attributes+"]
----
(
[ "$(oc get pod smi-h100 -n {gpu_namespace} -o jsonpath='{.status.phase}')" = Pending ] ||
  { echo "FAIL: smi-h100 is not Pending"; exit 1; }
oc get events -n {gpu_namespace} --field-selector involvedObject.name=smi-h100,reason=FailedScheduling \
  -o jsonpath='{.items[*].message}' | grep -q 'cannot allocate all claims' ||
  { echo "FAIL: no 'cannot allocate all claims' scheduling event for smi-h100"; exit 1; }
[ -z "$(oc get pods -n {gpu_namespace} --field-selector status.phase=Running -o name)" ] ||
  { echo "FAIL: another pod is running in {gpu_namespace}, so the GPU may not be free"; exit 1; }
echo PASS
)
----
====

删除永远无法被调度的 Pod：

[source,bash,role="execute",subs="attributes+"]
----
oc delete pod smi-h100 -n {gpu_namespace} --wait=true
----

预期结果：`pod "smi-h100" deleted`。

== 练习 7：两个 Pod 共享同一块 GPU

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m2-ex7.mp4[width=100%]

独立创建的 `ResourceClaim`（非由模板生成）是单次分配。每个命名该申请的 Pod 获得_相同_的设备。

[source,bash,role="execute",subs="attributes+"]
----
oc apply -n {gpu_namespace} -f - <<'EOF'
apiVersion: resource.k8s.io/v1
kind: ResourceClaim
metadata:
  name: shared-l4
spec:
  devices:
    requests:
    - name: gpu
      exactly:
        deviceClassName: gpu.nvidia.com
EOF
for p in share-a share-b; do
oc apply -n {gpu_namespace} -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: $p
spec:
  restartPolicy: Never
  tolerations: [{key: nvidia.com/gpu, operator: Exists, effect: NoSchedule}]
  securityContext: {runAsNonRoot: true, seccompProfile: {type: RuntimeDefault}}
  resourceClaims:
  - name: gpu
    resourceClaimName: shared-l4
  containers:
  - name: smi
    image: {cuda_image}
    command: ["bash", "-c", "nvidia-smi -L; sleep 3600"]
    securityContext: {allowPrivilegeEscalation: false, capabilities: {drop: [ALL]}}
    resources:
      claims: [{name: gpu}]
EOF
done
oc wait -n {gpu_namespace} --for=condition=Ready pod/share-a pod/share-b --timeout=300s
oc logs -n {gpu_namespace} share-a; oc logs -n {gpu_namespace} share-b
oc get resourceclaim shared-l4 -n {gpu_namespace} -o jsonpath='device: {.status.allocation.devices.results[0].device}{"\n"}reserved for: {.status.reservedFor[*].name}{"\n"}'
----

预期结果：两个 Pod 均 Ready，打印相同内容 `GPU 0: NVIDIA L4 (UUID: GPU-…)`，UUID 完全相同；申请分配到 `gpu-0`，并为 `share-a share-b` 保留。共享是申请的属性，在 API 中可见，而非隐藏的节点设置。两个进程共享 GPU 的显存和算力，彼此之间没有隔离，因此每个工作负载必须为另一个留出空间（第 2 天将为两个模型副本执行同样的操作）。

简言之：模板 = 每个 Pod 独占一个设备；独立申请 = 命名该申请的所有 Pod 共享同一设备。

释放 GPU，为模块 3 做准备：

[source,bash,role="execute",subs="attributes+"]
----
oc delete pod share-a share-b -n {gpu_namespace} --wait=true
oc get resourceclaim shared-l4 -n {gpu_namespace} -o jsonpath='reserved for: [{.status.reservedFor[*].name}] device: [{.status.allocation.devices.results[0].device}]{"\n"}'
----

预期结果：`reserved for: [] device: []`。申请仍然存在，但一旦没有 Pod 保留它，Kubernetes 就会释放其分配，GPU 便可供下一个申请使用。

== 检查点

继续之前，请确认您能够回答以下问题：

* `ResourceSlice` 向调度器提供了 `nvidia.com/gpu: 1` 无法提供的哪些信息？
* 哪个对象决定两个 Pod 是否共享 GPU，以及如何决定？
* 为什么 `smi-h100` 在 GPU 空闲时仍保持 `Pending`？
* `NVIDIADriver` CR 和 `GPUCluster` CR 各自负责什么，不负责什么？

.参考答案
[%collapsible]
====
* 设备是什么以及它提供什么：产品名、架构、显存、驱动和 CUDA 版本以及 PCI 位置，使工作负载可以按属性选择，并在分配中记录具体设备。
* 申请（Claim）。引用同一独立 `ResourceClaim` 的 Pod 共享其设备；引用 `ResourceClaimTemplate` 的 Pod 各自获得独立申请和独立设备。
* 其申请的 CEL 选择器要求 H100，而唯一设备的 `productName` 是 `NVIDIA L4`，所以没有设备匹配。
* `NVIDIADriver` 在 GPU 节点上运行驱动容器，加载内核模块。`GPUCluster` 运行 DRA kubelet 插件，通过该驱动发现 GPU 并以 ResourceSlice 形式发布（以及 DCGM exporter）。
====

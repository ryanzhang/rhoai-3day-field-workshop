= 模块 3：模型上线
:navtitle: 模块 3：模型上线

GPU 只有在运行模型后才有价值，而企业并不会让任意模型随意运行。他们需要知道模型来自哪里、生产中使用的是哪个版本，以及谁有权调用它。客户的问题是：_我如何将组织信任的模型记录在案，并在自有 GPU 上以认证方式提供服务？_

在本模块中，您将在 OpenShift AI 目录中找到红帽已验证的模型，创建一个模型注册表并记录该模型及其版本，然后使用模块 2 中申请的 GPU 通过 vLLM 提供服务，并验证哪些调用者有权限、哪些没有。

.初次接触 OpenShift AI 模型服务？
[%collapsible]
====
* *Modelcar* — 以 OCI 容器镜像（`oci://…`）打包的模型，像普通镜像一样拉取和缓存；无需 S3 存储桶或凭据。
* *模型注册表* — 记录已注册模型、其版本以及每个版本的制品（文件所在位置）和元数据的服务。
* *KServe* — OpenShift AI 的服务层；`InferenceService` 声明一个模型服务器。
* *ServingRuntime* — KServe 运行的服务器容器模板，本例中使用面向 NVIDIA GPU 的 vLLM。
* *vLLM* — 推理引擎；将模型加载到 GPU 上并管理 KV cache（每个 token 的缓存内存，使其能同时处理多个请求）。
====

== 技术背景

模型上线分三个步骤，分别由不同组件负责：

[cols="1,2,2",options="header"]
|===
| 步骤 | 组件 | 记录或执行的内容

| 选择
| 模型目录（`{registry_namespace}` 中的 `model-catalog` 服务）
| 列出红帽已验证的模型，包括大小、许可证、任务以及每个模型的 modelcar 镜像

| 记录
| 模型注册表（您创建的 `ModelRegistry`；kube-rbac-proxy 后面的 REST API）
| 已注册模型 → 版本 → 制品（`oci://` URI 和模型格式）

| 服务
| KServe `InferenceService` + vLLM `ServingRuntime`
| 一个 Deployment，其 Pod 拉取 modelcar，通过 DRA 申请 GPU，并在认证后暴露兼容 OpenAI 的 API
|===

模型为 *{model_display}*：一个 70 亿参数的混合模型（Transformer 层与 Mamba 状态空间层交替），每个 token 仅激活约 10 亿参数（专家混合架构），并以 FP8 量化。在 L4 上，权重约需 6.6 GiB，剩余空间可用于大型 KV cache 以及第 2 天的两个副本。

认证通过一个注解开启：`security.opendatahub.io/enable-auth: "true"`。KServe 随后在 vLLM 前放置一个 kube-rbac-proxy：每个请求都必须携带 OpenShift bearer token，且该 token 的身份必须被允许对 InferenceService 执行 `get` 操作。

// NOT-IN-DOCS: OpenShift AI 3.5 通过硬件配置文件（设备插件）记录 GPU 服务。在 InferenceService predictor 中用 resourceClaims 请求 GPU 是 DRA 原生方式，KServe CRD 接受，但不是有文档的 OpenShift AI 过程。
NOTE: OpenShift AI {rhoai_version} 通过硬件配置文件（请求 `nvidia.com/gpu`）记录 GPU 服务。在仅有 DRA 的 GPU 节点上不存在此类资源，因此本模块在 InferenceService 中使用 `resourceClaims` 请求 GPU——KServe API 接受该字段。详见 xref:91-reference.adoc[技术参考]。

== 学习目标

* 在模型目录中找到已验证的模型及其 modelcar 镜像。
* 创建模型注册表，并通过 REST API 记录模型、版本及其制品。
* 使用 DRA 申请的 GPU 通过 vLLM 提供模型服务，并开启认证。
* 验证匿名调用者和未授权调用者被拒绝，授权调用者可正常访问。
* 读取 vLLM 的启动报告：权重内存、KV cache 大小和最大并发数。

== 练习 2：创建模型注册表

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m3-ex2.mp4[width=100%]

目录是红帽的列表。注册表是_您的_：它记录您的组织决定使用的内容。OpenShift AI 的模型注册表 Operator 通过一个 CR 部署注册表。

[source,yaml,subs="attributes+"]
----
kind: ModelRegistry
metadata:
  name: {registry_name}
  namespace: {registry_namespace}   # <1>
spec:
  postgres:
    generateDeployment: true        # <2>
  rest: {}                          # <3>
  kubeRBACProxy: {}                 # <4>
----
<1> *namespace* — DataScienceCluster 为注册表指定的命名空间（`registriesNamespace`）。
<2> *generateDeployment* — Operator 为注册表元数据部署 PostgreSQL 数据库。
<3> *rest* — 暴露 REST API。
<4> *kubeRBACProxy* — 在 REST API 前加 OpenShift 认证和 RBAC，并创建 Route。

从现在起，命令会将您的 OpenShift token（集群管理员凭据）发送到集群端点，因此会先验证服务器：以下代码块保存系统 CA 以及签署集群入口证书的证书链（某些集群为自签名，RHDP 订单上为公开签名的），并通过 `CURL_CA_BUNDLE` 告知 `curl` 使用该证书。本工作坊中没有任何命令使用 `curl -k` 加 token 或密钥。

[source,bash,role="execute",subs="attributes+"]
----
{ cat /etc/pki/tls/certs/ca-bundle.crt; oc get configmap default-ingress-cert -n openshift-config-managed -o jsonpath='{.data.ca-bundle\.crt}'; } > ~/ingress-ca.crt
export CURL_CA_BUNDLE=~/ingress-ca.crt
oc apply -f - <<'EOF'
apiVersion: modelregistry.opendatahub.io/v1beta1
kind: ModelRegistry
metadata:
  name: {registry_name}
  namespace: {registry_namespace}
spec:
  postgres:
    generateDeployment: true
  rest: {}
  kubeRBACProxy: {}
EOF
oc wait modelregistries.modelregistry.opendatahub.io/{registry_name} -n {registry_namespace} --for=condition=Available --timeout=300s
REGISTRY=https://$(oc get route {registry_name}-https -n {registry_namespace} -o jsonpath='{.spec.host}')/api/model_registry/v1alpha3
echo "$REGISTRY"
----

预期结果：`~/ingress-ca.crt` 已写入，`modelregistry.modelregistry.opendatahub.io/{registry_name} condition met`，以及注册表 URL `https://{registry_name}-rest.{cluster_domain}/api/model_registry/v1alpha3`。

== 练习 3：记录模型、版本及制品

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m3-ex3.mp4[width=100%]

首先进行负向验证：注册表必须拒绝匿名调用者。

[source,bash,role="execute"]
----
curl -s -o /dev/null -w 'anonymous: %{http_code}\n' "$REGISTRY/registered_models"
----

预期结果：`anonymous: 401`。kube-rbac-proxy 拒绝没有 token 的请求。

现在记录模型、版本 `3.0` 以及指向 modelcar 的制品。每条记录只在按名称查找不到时才创建，因此该代码块可以安全地重复运行：

[source,bash,role="execute",subs="attributes+"]
----
AUTH="Authorization: Bearer $(oc whoami -t)"
reg() { curl -s -H "$AUTH" -H 'Content-Type: application/json' "$@"; }
RM_ID=$(reg "$REGISTRY/registered_model?name=granite-4.0-h-tiny-fp8" | jq -r '.id // empty')
[ -n "$RM_ID" ] || RM_ID=$(reg -X POST "$REGISTRY/registered_models" \
  -d "{\"name\":\"granite-4.0-h-tiny-fp8\",\"description\":\"{model_display}, Red Hat validated\",\"owner\":\"$(oc whoami)\"}" | jq -r .id)
MV_ID=$(reg "$REGISTRY/model_version?name=3.0&parentResourceId=$RM_ID" | jq -r '.id // empty')
[ -n "$MV_ID" ] || MV_ID=$(reg -X POST "$REGISTRY/model_versions" \
  -d "{\"name\":\"3.0\",\"registeredModelId\":\"$RM_ID\",\"author\":\"$(oc whoami)\"}" | jq -r .id)
[ "$(reg "$REGISTRY/model_versions/$MV_ID/artifacts" | jq '.size')" -gt 0 ] || reg -X POST "$REGISTRY/model_versions/$MV_ID/artifacts" \
  -d '{"artifactType":"model-artifact","name":"granite-4.0-h-tiny-fp8-modelcar","uri":"{model_uri}","modelFormatName":"vLLM","modelFormatVersion":"1"}' >/dev/null
echo "registered model id: $RM_ID, version id: $MV_ID"
reg "$REGISTRY/model_versions/$MV_ID/artifacts" | jq '.items[] | {name, uri, modelFormatName}'
reg "$REGISTRY/registered_models/$RM_ID/versions" | jq -r '.items[] | "\(.name) \(.state)"'
----

预期结果：`registered model id: 1, version id: 2`（全新注册表的 ID）；一个制品，`"uri": "{model_uri}"`，`"modelFormatName": "vLLM"`；版本列表显示 `3.0 LIVE`。注册表现在可以回答"这个模型的 3.0 版本对应哪个镜像"。

图形界面视图：在 OpenShift AI 控制台中，*AI hub* → *Models* → *Registry* 标签页，模型注册表 `{registry_name}`：模型 `granite-4.0-h-tiny-fp8`，最新版本 `3.0`，所有者为您的用户，*Deployments* 显示 `-`（尚未部署）。

== 练习 4：准备服务 Project

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m3-ex4.mp4[width=100%]

创建一个用于模型的数据科学 Project 和 GPU 申请模板，然后编写 `ServingRuntime`：KServe 为每个命名该 Runtime 的 InferenceService 运行的容器。OpenShift AI 控制台通过内置模板（`vllm-cuda-runtime-template`）创建相同的对象；这里您手动编写，以便了解 Runtime 本质上只是一个容器规格加上它所服务的模型格式。

[source,bash,role="execute",subs="attributes+"]
----
oc new-project {model_namespace} >/dev/null 2>&1 || oc project {model_namespace}
oc label namespace {model_namespace} opendatahub.io/dashboard=true --overwrite
oc apply -n {model_namespace} -f - <<'EOF'
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: one-l4
spec:
  spec:
    devices:
      requests:
      - name: gpu
        exactly:
          deviceClassName: gpu.nvidia.com
          selectors:
          - cel:
              expression: device.attributes['gpu.nvidia.com'].productName == 'NVIDIA L4'
EOF
----

预期结果：Project `{model_namespace}` 存在，带有标签 `opendatahub.io/dashboard=true`（使控制台列出该 Project），以及 `resourceclaimtemplate.resource.k8s.io/one-l4 created`。

Runtime 的关键字段：

[source,yaml,subs="attributes+"]
----
kind: ServingRuntime
spec:
  supportedModelFormats:
  - {name: vLLM, autoSelect: true}                       # <1>
  containers:
  - name: kserve-container                               # <2>
    image: {vllm_image}   # <3>
    command: [python, -m, vllm.entrypoints.openai.api_server]
    args: [--port=8080, --model=/mnt/models, "--served-model-name={{.Name}}"]   # <4>
    ports: [{containerPort: 8080, protocol: TCP}]
----
<1> *supportedModelFormats* — `modelFormat` 为 `vLLM` 的 InferenceService 可以使用此 Runtime。
<2> *kserve-container* — KServe 期望的名称；InferenceService 的 `args`、`resources` 和存储会被合并到此容器中。
<3> *image* — OpenShift AI {rhoai_version} 附带的 vLLM 红帽构建（Red Hat AI Inference Server），通过摘要固定版本。
<4> *args* — `/mnt/models` 是 KServe 挂载 modelcar 文件的位置；`{{.Name}}` 变为 InferenceService 名称，客户端以此作为 `model` 参数发送请求。

[source,bash,role="execute",subs="attributes+"]
----
oc apply -n {model_namespace} -f - <<'EOF'
apiVersion: serving.kserve.io/v1alpha1
kind: ServingRuntime
metadata:
  name: vllm-cuda-runtime
  labels:
    opendatahub.io/dashboard: "true"
  annotations:
    openshift.io/display-name: vLLM NVIDIA GPU ServingRuntime for KServe
    opendatahub.io/runtime-version: v0.24.0
spec:
  annotations:
    opendatahub.io/kserve-runtime: vllm
    prometheus.io/path: /metrics
    prometheus.io/port: "8080"
  multiModel: false
  supportedModelFormats:
  - name: vLLM
    autoSelect: true
  containers:
  - name: kserve-container
    image: {vllm_image}
    command: ["python", "-m", "vllm.entrypoints.openai.api_server"]
    args: ["--port=8080", "--model=/mnt/models", "--served-model-name={{.Name}}"]
    env:
    - name: HF_HOME
      value: /tmp/hf_home
    ports:
    - containerPort: 8080
      protocol: TCP
EOF
echo "yours:    $(oc get servingruntime vllm-cuda-runtime -n {model_namespace} -o jsonpath='{.spec.containers[0].image}')"
echo "template: $(oc process -n redhat-ods-applications vllm-cuda-runtime-template -o jsonpath='{.items[0].spec.containers[0].image}')"
----

预期结果：`servingruntime.serving.kserve.io/vllm-cuda-runtime created`，两行镜像地址完全相同：您编写的 Runtime 与控制台使用的 vLLM 构建完全一致。

== 练习 5：在申请的 GPU 上提供模型服务

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m3-ex5.mp4[width=100%]

[source,yaml,subs="attributes+"]
----
kind: InferenceService
metadata:
  annotations:
    serving.kserve.io/deploymentMode: RawDeployment          # <1>
    security.opendatahub.io/enable-auth: "true"              # <2>
  labels:
    modelregistry.opendatahub.io/registered-model-id: "<RM_ID>"   # <3>
spec:
  predictor:
    resourceClaims:
    - {name: gpu, resourceClaimTemplateName: one-l4}         # <4>
    model:
      storageUri: {model_uri}
      args: ["--max-model-len=16384", "--enable-auto-tool-choice", "--tool-call-parser=granite4"]   # <5>
----
<1> *deploymentMode* — 普通 Deployment 和 Service（无 Knative）；LLM 的标准模式。
<2> *enable-auth* — 在 vLLM 前加 kube-rbac-proxy；调用者需要 token 和 RBAC 权限。
<3> *registry labels* — 标记此部署来自哪个注册表、模型和版本，这是控制台从注册表部署时设置的标签。这些标签不会告知注册表任何信息；练习 6 负责此操作。
<4> *resourceClaims* — GPU 申请方式与模块 2 中的测试 Pod 完全相同。
<5> *vLLM args* — 上下文长度，以及使用 Granite 4 解析器的工具调用（第 3 天使用）。

[source,bash,role="execute",subs="attributes+"]
----
oc apply -n {model_namespace} -f - <<EOF
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: {model_name}
  annotations:
    serving.kserve.io/deploymentMode: RawDeployment
    security.opendatahub.io/enable-auth: "true"
  labels:
    networking.kserve.io/visibility: exposed
    modelregistry.opendatahub.io/name: {registry_name}
    modelregistry.opendatahub.io/registered-model-id: "$RM_ID"
    modelregistry.opendatahub.io/model-version-id: "$MV_ID"
spec:
  predictor:
    tolerations: [{key: nvidia.com/gpu, operator: Exists, effect: NoSchedule}]
    resourceClaims:
    - name: gpu
      resourceClaimTemplateName: one-l4
    model:
      modelFormat: {name: vLLM}
      runtime: vllm-cuda-runtime
      storageUri: {model_uri}
      args: ["--max-model-len=16384", "--enable-auto-tool-choice", "--tool-call-parser=granite4"]
      resources:
        requests: {cpu: "2", memory: 12Gi}
        limits: {cpu: "6", memory: 20Gi}
        claims: [{name: gpu}]
EOF
----

预期结果：`inferenceservice.serving.kserve.io/{model_name} created`。

拉取 modelcar 和启动 vLLM 需要几分钟。等待 `Ready`：

[source,bash,role="execute",subs="attributes+"]
----
oc wait isvc/{model_name} -n {model_namespace} --for=condition=Ready --timeout=900s
oc get isvc {model_name} -n {model_namespace} -o jsonpath='{.status.url}{"\n"}'
oc get resourceclaims -n {model_namespace} \
  -o custom-columns=CLAIM:.metadata.name,DEVICE:.status.allocation.devices.results[0].device,RESERVED_FOR:.status.reservedFor[*].name
----

预期结果：`inferenceservice.serving.kserve.io/{model_name} condition met`；URL 为 `https://{model_name}-{model_namespace}.{cluster_domain}`；一个申请 `{model_name}-predictor-…-gpu-…` 分配到 `gpu-0` 并为 predictor Pod 保留。模型服务器通过与测试 Pod 相同的 DRA 机制持有 GPU。

== 练习 6：在注册表中记录部署信息

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m3-ex6.mp4[width=100%]

注册表不会监视集群。只有在有人记录时，它才知道某个部署的存在，而当您从注册版本点击 *Deploy model* 时，控制台就会完成此操作。注册表的模型很简单：一个_服务环境_（此处为您的 Project）包含多个_推理服务_，每个服务指向一个已注册的模型和版本。记录您的部署：

[source,bash,role="execute",subs="attributes+"]
----
SE_ID=$(reg "$REGISTRY/serving_environment?name={model_namespace}" | jq -r '.id // empty')
[ -n "$SE_ID" ] || SE_ID=$(reg -X POST "$REGISTRY/serving_environments" -d '{"name":"{model_namespace}"}' | jq -r .id)
[ -n "$(reg "$REGISTRY/inference_service?name={model_name}&parentResourceId=$SE_ID" | jq -r '.id // empty')" ] ||
  reg -X POST "$REGISTRY/serving_environments/$SE_ID/inference_services" \
    -d "{\"name\":\"{model_name}\",\"registeredModelId\":\"$RM_ID\",\"modelVersionId\":\"$MV_ID\",\"runtime\":\"vllm-cuda-runtime\",\"desiredState\":\"DEPLOYED\",\"servingEnvironmentId\":\"$SE_ID\"}" \
    | jq -r 'if .id then "recorded: \(.name)" else "registry refused: \(.message // .)" end'
reg "$REGISTRY/inference_services" | jq -r '.items[] | "\(.name) model=\(.registeredModelId) version=\(.modelVersionId) \(.desiredState)"'
----

预期结果：首次运行显示 `recorded: {model_name}`（重新运行时跳过记录，只打印列表），然后 `{model_name} model=1 version=2 DEPLOYED`（全新注册表的 ID）：注册表现在记录了哪个版本在 `{model_namespace}` 中运行。注册表现在可以回答"3.0 版本在哪里运行？"。

图形界面视图：刷新 *AI hub* → *Models* → *Registry*：`granite-4.0-h-tiny-fp8` 的 *Deployments* 列现在显示 `1 deployment`。

== 练习 7：验证哪些调用者可以访问模型

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m3-ex7.mp4[width=100%]

三种调用者：匿名用户、没有权限的 ServiceAccount，以及您本人。

[source,bash,role="execute",subs="attributes+"]
----
URL=$(oc get isvc {model_name} -n {model_namespace} -o jsonpath='{.status.url}')
oc create sa no-rights -n {model_namespace} --dry-run=client -o yaml | oc apply -f - >/dev/null
curl -s -o /dev/null -w 'anonymous:          %\{http_code}\n' "$URL/v1/models"
curl -s -o /dev/null -w 'SA without RBAC:    %\{http_code}\n' -H "Authorization: Bearer $(oc create token no-rights -n {model_namespace})" "$URL/v1/models"
curl -s -o /dev/null -w 'you (cluster-admin): %\{http_code}\n' -H "Authorization: Bearer $(oc whoami -t)" "$URL/v1/models"
----

预期结果：`anonymous: 401`，`SA without RBAC: 403`，`you (cluster-admin): 200`。401 表示"您是谁？"（无 token）；403 表示"我知道您是谁，但您没有权限"（该 ServiceAccount 无法 `get` InferenceService）。

现在向模型提问，并附带它可能决定调用的工具：

[source,bash,role="execute",subs="attributes+"]
----
curl -s "$URL/v1/chat/completions" -H "Authorization: Bearer $(oc whoami -t)" -H 'Content-Type: application/json' -d '{
  "model": "{model_name}",
  "messages": [{"role": "user", "content": "What is the weather in Seoul right now?"}],
  "tools": [{"type": "function", "function": {"name": "get_weather", "description": "Current weather for a city",
             "parameters": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]}}}],
  "max_tokens": 200}' | jq '{finish: .choices[0].finish_reason, tool_calls: .choices[0].message.tool_calls, usage}'
----

预期结果：`"finish": "tool_calls"` 以及对 `get_weather` 的一次工具调用，参数为 `{"city": "Seoul"}`，外加统计 prompt 和补全 token 的 `usage` 块。模型没有直接回答，而是要求调用者运行一个工具。这就是第 3 天 Agent 的基础构建块。

== 练习 8：读取 vLLM 对 GPU 的使用情况

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m3-ex8.mp4[width=100%]

vLLM 在启动时报告它如何分配 GPU 显存。

[source,bash,role="execute",subs="attributes+"]
----
oc logs -n {model_namespace} deploy/{model_name}-predictor -c kserve-container \
  | grep -o -E 'Model loading took [0-9.]+ GiB|Available KV cache memory: [0-9.]+ GiB|GPU KV cache size: [0-9,]+ tokens|Maximum concurrency for [0-9,]+ tokens per request: [0-9.]+x' | sort -u
----

预期结果：`Model loading took 6.64 GiB`，`Available KV cache memory: 12.25 GiB`，KV cache 约 130 万个 token，以及在最大 16,384 token 上下文下最大并发约 80 个请求。权重是固定的；vLLM 能分配的所有剩余显存都变成 KV cache，KV cache 决定了可以同时处理多少个请求。混合 Mamba 模型每个 token 所需的缓存远少于纯 Transformer，这就是为什么这个数字如此之大。

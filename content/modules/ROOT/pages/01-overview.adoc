:navtitle: 架构与控制边界

== 核心问题

实验针对客户常问的问题给出答案，并通过集群中的真实证据加以验证：

. 工作负载如何获取 GPU？工作负载可以共享一个 GPU 吗？（模块 2）
. 如何接入、记录并提供组织信任的模型，谁可以调用它？（模块 3）
. llm-d 相比单个 vLLM 服务器增加了什么？我如何看到这些效果？（模块 4）
. 如何将模型作为受治理的内部服务对外提供？（模块 5 和 6）
. 应用程序和 Agent 如何消费它，我如何查看 Agent 的操作记录？（模块 6 和 7）
. 如何确认模型质量足够好？如何保持模型安全？（模块 8 和 9）

== 技术栈

[cols="1,2,3",options="header"]
|===
| 层次 | 组件 | 职责

| 硬件发现
| Node Feature Discovery
| 为节点打上发现的硬件标签（NVIDIA 对应 `pci-10de.present`）

| GPU 驱动
| NVIDIA GPU Operator，`NVIDIADriver` CR
| 在 GPU 节点上加载 NVIDIA 内核驱动

| GPU 分配
| NVIDIA DRA 驱动（`GPUCluster` CR）+ Kubernetes DRA
| 将 GPU 发布为 ResourceSlice；调度器将其分配给 ResourceClaim

| 模型清单
| OpenShift AI 模型目录与模型注册表
| 已验证的模型（目录）；你的模型、版本及制品（注册表）

| 模型服务
| KServe + vLLM（Red Hat AI Inference Server 构建版）
| 在 GPU 上运行模型；提供 OpenAI 兼容 API；通过 kube-rbac-proxy 进行身份验证

| 推理路由
| llm-d（`LLMInferenceService`、端点选择器、InferencePool）
| 根据服务器状态为每个请求选择副本

| 服务治理
| 模型即服务 + Red Hat Connectivity Link（在 Gateway API 网关上运行）
| API 密钥、订阅（分层）、token 限速、使用量遥测

| 应用信任
| MLflow、EvalHub（TrustyAI）、NeMo Guardrails（TrustyAI）
| 链路追踪、质量评测、输入与输出策略
|===

== 一个必须能够解释的关键区别

*使 GPU 可用不等同于使其可被调度。* 驱动让节点上的进程可以使用 GPU；而只有对调度器可见的资源——设备插件的计数器或 DRA 的描述设备——才能让 Kubernetes 决定哪个 Pod 获得它。使用 DRA 时，申请（ResourceClaim）是记录分配决策的地方，包括设备是否被共享。GPU 层之上的一切——模型服务器、副本、MaaS 分层——都依赖于该分配。

== 实验进程

=== 第一天：从 GPU 到模型服务

模块 1 进行环境清点：GPU 节点存在，但没有任何工作负载可以使用它。模块 2 加载驱动、开启 DRA，并以三种方式申请 GPU。模块 3 通过目录和你自己的注册表接入一个已验证的模型，并在申请的 GPU 上使用 vLLM 对外提供服务，同时开启身份验证。

=== 第二天：从模型到服务

模块 4 用两个共享 GPU 的 llm-d 副本替换单个服务器，并观察调度器的路由行为。模块 5 搭建模型即服务。模块 6 以分层、密钥和限额的方式发布模型，并从应用程序中消费它。

=== 第三天：从服务到可信应用

模块 7 使用 MLflow 追踪 Agent。模块 8 使用 EvalHub 评测模型。模块 9 使用 NeMo Guardrails 守护模型并对防护效果进行测量。

== 解读注意事项

* 每个参与者集群只有一块 L4 GPU，展示的是机制，而非生产环境的容量或性能。你看到的延迟和吞吐量数据仅适用于该硬件。
* 通过共享申请在两个进程之间共享一块 GPU，并不提供内存或计算的隔离；展示此方式是为了教授 API 用法，而非作为多租户隔离方案。
* 部分步骤使用的 API 比 OpenShift AI {rhoai_version} 文档中更新（每页均有标注，并汇总在 xref:91-reference.adoc[技术参考] 中）。在此通过测试并不意味着它们是受支持的配置。

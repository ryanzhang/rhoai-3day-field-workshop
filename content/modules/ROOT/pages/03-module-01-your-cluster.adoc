= 模块 1：您的集群
:navtitle: 模块 1：您的集群

本工作坊中的每个练习都会对真实的 OpenShift 集群进行更改，每个结论都会通过集群的实际报告加以验证。在进行任何更改之前，您需要先确认自己的身份、集群已有的资源以及尚未配置的内容。本模块背后的客户问题，是平台团队最常问的第一个问题：_这个集群今天有什么？要运行 AI 工作负载，我们还需要添加什么？_

在本模块中，您将打开 Web Terminal，确认自己的身份和权限，并对 GPU 节点、已安装的 Operator 以及 OpenShift AI 进行清点。

.初次接触此环境？
[%collapsible]
====
* *Web Terminal* — 在集群上某个 Pod 中运行的终端，直接在 OpenShift 控制台内打开；以您的身份登录，拥有您的权限。
* *Operator* — 通过自定义资源（CR）在集群上安装和管理产品的控制器。
* *OLM（Operator 生命周期管理器）* — 从目录中安装 Operator；`Subscription` 用于请求某个 Operator，`ClusterServiceVersion`（CSV）是已安装的版本。
* *DataScienceCluster（DSC）* — OpenShift AI 的资源，用于开启或关闭各组件（控制台、KServe、模型注册表等）。
* *NFD（Node Feature Discovery，节点特性发现）* — 为每个节点打上其硬件标签，例如 GPU 的 PCI 厂商 ID。
====

== 技术背景

您的集群由 OpenShift GitOps 准备，仅安装了以下 Operator：Node Feature Discovery、NVIDIA GPU Operator、Red Hat Connectivity Link 和 Web Terminal，以及已有的 OpenShift AI {rhoai_version} 安装。这些组件均尚未针对本工作坊进行配置。集群中有一个 GPU 节点，但目前没有任何组件可以使用该 GPU：硬件发现尚未运行，驱动程序尚未加载，调度器也无法感知到 GPU 资源。您将自行添加每一个缺失的层，以 YAML 形式编写并应用，使得在第一天结束时，您能够解释每一层的作用。

整个过程中您以自己的身份操作。由于多个实验需要修改集群范围的配置（驱动程序、设备类、网关），您的用户在这个专属集群上拥有集群管理员权限。Showroom 终端被故意关闭：Showroom 页面没有登录保护，若在那里提供终端，任何拥有 URL 的人都能获得您的集群管理员权限。

== 学习目标

* 打开 Web Terminal 并确认其操作身份。
* 使用 `oc auth can-i` 确认集群管理员权限。
* 通过污点（taint）找到 GPU 节点，并确认集群目前既无法识别也无法调度该 GPU。
* 查看已安装的 Operator 和 OpenShift AI 组件。

== 练习 1：打开 Web Terminal 并确认身份

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m1-ex1.mp4[width=100%]

. 如果控制台显示 *Welcome to the new OpenShift experience!*（首次登录时会出现），点击 *Skip tour*。
. 在 OpenShift 控制台中，点击顶部栏的 *Command line terminal* 图标（*>_*）。若浏览器窗口较窄，该图标会折叠进 *Utility menu*（*⋮*）。
. 底部弹出 *OpenShift command line terminal* 面板，显示 *Initialize terminal*。保持 *Project* 为 `openshift-terminal`，点击 *Start*。
. 等待面板显示 `Welcome to the OpenShift Web Terminal` 和 `bash` 提示符。

image::03-web-terminal-start.png[初始化终端面板，显示 Project openshift-terminal 和 Start 按钮]

NOTE: 终端在 15 分钟无输入后会自动停止（默认空闲超时），Shell 变量也会随之消失。如果预计需要离开，请在点击 *Start* 前在 *Initialize terminal* 面板中设置更长的 *Timeout*。若终端已停止，重新打开并从当前模块的第一个练习重新开始。

TIP: 如需更大的操作空间，可在新的浏览器标签页中全屏打开同一终端：
link:https://console-openshift-console.{cluster_domain}/terminal[console-openshift-console.{cluster_domain}/terminal^]。
步骤视频使用的就是该视图。

然后运行：

[source,bash,role="execute"]
----
oc whoami
oc auth can-i '*' '*' --all-namespaces
----

预期结果：`oc whoami` 打印您的用户名（由培训师提供，例如 `kuro`），`oc auth can-i` 打印 `yes`：您的用户可对任何资源执行任何操作，即集群管理员权限。后续所有命令均以此权限运行。终端内置 `oc`、`jq`、`curl` 和 `git`；本指南不使用其他工具。

简言之：您是集群管理员，以自己的身份操作，终端运行在集群上。

== 练习 2：找到 GPU 节点

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m1-ex2.mp4[width=100%]

GPU 节点添加时携带了污点 `nvidia.com/gpu`，以阻止普通 Pod 调度到这个高价值节点：只有容忍该污点的 Pod 才会被调度到这里。通过污点找到该节点：

[source,bash,role="execute"]
----
oc get nodes -o custom-columns=NODE:.metadata.name,INSTANCE:.metadata.labels.node\\.kubernetes\\.io/instance-type,TAINTS:.spec.taints[*].key \
  | grep -E 'NODE|nvidia.com/gpu'
----

预期结果：显示标题行和一个节点，实例类型为 `g6.2xlarge`（8 个 vCPU 和一块 NVIDIA L4 GPU），污点为 `nvidia.com/gpu`。

== 练习 3：确认 GPU 当前不可用（负向验证）

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m1-ex3.mp4[width=100%]

GPU 可用需要三个条件：能识别节点上硬件的组件、内核驱动程序，以及让调度器感知并分配设备的机制。逐一检查：

[source,bash,role="execute"]
----
GPU_NODE=$(oc get nodes -o custom-columns=NODE:.metadata.name,TAINTS:.spec.taints[*].key --no-headers | awk '/nvidia.com\/gpu/ {print $1; exit}')
echo "NVIDIA PCI label on $GPU_NODE: $(oc get node "$GPU_NODE" -o jsonpath='{.metadata.labels.feature\.node\.kubernetes\.io/pci-10de\.present}')"
echo "allocatable on $GPU_NODE:"; oc get node "$GPU_NODE" -o jsonpath='{.status.allocatable}{"\n"}'
echo "GPU device classes:"; oc get deviceclass -o name | grep nvidia || echo "none"
echo "driver pods:"; oc get pods -n nvidia-gpu-operator -o name | grep -E 'driver|dra' || echo "none"
----

预期结果：`NVIDIA PCI label on <node>:` 后面为空（硬件发现尚未运行）；allocatable 为 `{"cpu":"7500m","ephemeral-storage":…,"memory":"29423584Ki","pods":"250"}`，不含 `nvidia.com/gpu`；`GPU device classes:` 打印 `none`；`driver pods:` 打印 `none`。硬件存在，但集群既不知道这是 GPU，也无法将任何 Pod 调度到它上面。模块 2 将添加缺失的各层。

== 练习 4：清点 Operator 和 OpenShift AI

.视频：本练习在测试集群上以参与者身份运行（等待时间已加速）
video::m1-ex4.mp4[width=100%]

[source,bash,role="execute"]
----
oc get csv -A --no-headers 2>/dev/null | awk '{print $2, $NF}' | sort -u | grep -E 'nfd|gpu-operator|rhcl|authorino|limitador|web-terminal|rhods'
oc get datasciencecluster -o jsonpath='{range .items[*].status.conditions[?(@.status=="True")]}{.type}{"\n"}{end}' | grep -E 'Ready|KserveReady|ModelRegistryReady|DashboardReady'
----

预期结果：每个列出的 CSV 均显示 `Succeeded`：`nfd.4.20…`、`gpu-operator-certified.v{gpu_operator_version}`、`rhcl-operator.v1.4.3` 及其依赖的 `authorino-operator` 和 `limitador-operator`、`web-terminal.v1.17.1` 和 `rhods-operator.3.5.2`（OpenShift AI {rhoai_version}）。DataScienceCluster 条件包含 `Ready`、`KserveReady`、`ModelRegistryReady` 和 `DashboardReady`。Operator 已安装，但尚未进行任何配置。

.本模块的脚本化断言
[%collapsible]
====
[source,bash]
----
(
[ "$(oc auth can-i '*' '*' --all-namespaces)" = yes ] || { echo "FAIL: not cluster-admin"; exit 1; }
oc get nodes -o custom-columns=T:.spec.taints[*].key --no-headers | grep -q nvidia.com/gpu || { echo "FAIL: no GPU node"; exit 1; }
for p in nfd gpu-operator-certified rhcl-operator web-terminal rhods-operator; do
  oc get csv -A --no-headers 2>/dev/null | awk '{print $2, $NF}' | grep -q "^$p.* Succeeded$" || { echo "FAIL: operator $p not Succeeded"; exit 1; }
done
echo PASS
)
----
====

== 检查点

继续之前，请确认您能够回答以下问题：

* 您是如何找到 GPU 节点的？什么机制阻止了普通 Pod 调度到该节点？
* 在 Pod 能够使用 GPU 之前，缺少哪三个层？
* 为什么本工作坊关闭了 Showroom 终端？

.参考答案
[%collapsible]
====
* 通过 `nvidia.com/gpu` 污点找到；该污点会阻止所有不容忍它的 Pod 调度到该节点。
* 硬件发现（尚无 NFD 标签）、内核驱动程序（无驱动程序 Pod）、以及调度器可见的设备（既无设备插件资源，也无 DRA 设备类）。
* Showroom 页面没有登录保护；终端放在那里会将您的集群管理员权限暴露给任何拥有 URL 的人。
====
